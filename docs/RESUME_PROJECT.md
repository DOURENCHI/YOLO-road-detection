## 0. 先把边界划清楚

**这个项目是什么**：一个道路场景的**多类别目标检测基线**，加上围绕它做的一套**数据与评估工程闭环**。
你在里面真做的事是：把一份混乱的公开标注整理干净 → 训出一个能用的模型 → 用一套有纪律的方法评估它 → 把过程中踩的坑写成可复现的脚本和记录。

**这个项目不是什么**（这几句话千万别在简历或面试里写）：

| 不能说的 | 为什么 |
|---|---|
| "自动驾驶感知系统" | 12 类、814 张图的公开数据集，没有时序、没有多传感器、没有恶劣天气验证 |
| "部署 / 推理加速" | 阶段四（ONNX / TensorRT）**没做**，你只做了 PyTorch 侧的性能测量 |
| "设计了检测算法 / 改了网络结构" | 用的是 Ultralytics 现成的 YOLO26n，你没动过网络 |
| "实现了多目标跟踪算法" | 调的是框架内置的 ByteTrack，你没改关联算法 |
| "mAP 超过某某论文" | 跨数据集比 mAP 没有意义 |

一句话定位：**"我独立做了一次完整的检测训练与评估，并且清楚它的每一步为什么这么做、以及它现在还不够用在哪里。"**
这个定位不虚，而且比乱吹更难被问倒。

## 1. 简历条目（可直接复制）

### 1.1 精简版（版面紧张时用这三行）

**道路场景多类别目标检测（YOLO26n）｜个人项目｜2026.10**
- 独立完成 814 张图 / 12 类公开数据集的数据整理与清洗，统一 860 个多边形标注为检测框，异常 0；
- 训练 YOLO26n 并用留出测试集评估：**mAP50 0.680 / mAP50-95 0.423**，FP32 单张端到端 **16.4 ms**；
- 交付 10 个可复现脚本、评估报告与 README，形成可复现的数据 → 训练 → 评估闭环。

### 1.2 完整版（五条，推荐）

**道路场景多类别目标检测（YOLO26n）｜个人项目｜2026.10**

- **数据工程**：把公开数据集（Roboflow RF100 · road-traffic，814 张图 / 12 类 / 3,165 个框）中混排的矩形框与多边形两种标注统一成 YOLO 检测格式，转换 860 个多边形实例；坐标越界、格式异常均为 0，并输出可审计的转换报告。
- **模型训练**：在单卡 RTX 5060 Laptop 上用 YOLO26n 完成 50 轮训练（imgsz 640 / batch 8，耗时约 11 分钟）；通过训练集与验证集的分类损失曲线分离判定出过拟合，并定位到 4 个长尾类因训练样本仅 1~32 个框而指标显著偏低。
- **评估与验证**：在留出的测试集（133 张图）上做一次性正式评估，得 **mAP50 0.680 / mAP50-95 0.423 / 精确率 0.787 / 召回率 0.627**；用 F1–置信度曲线确定最优阈值 0.30，与默认值 0.25 吻合。
- **推理性能**：设计三档计时口径（纯 GPU 前向 / 框架内置阶段拆分 / 完整端到端），测得 FP32 单张端到端 **16.4 ms**（约 61 FPS），批量 8 时吞吐提升约 2 倍；两轮重复测量确认 FP32 稳定，并据此**放弃** FP16（两轮波动达 57%）。
- **工程质量**：交付 10 个可独立运行的脚本 + README + 评估报告；为「测试集只能看一次」「改标签必须清缓存」「框架输出路径按当前目录解析」等 6 个实际踩过的坑留下记录与检查脚本。

### 1.3 技术栈行

`Python` · `PyTorch` · `Ultralytics YOLO` · `OpenCV` · `NumPy` · `Matplotlib` · `Git` · 目标检测 / 数据清洗 / 模型评估

> 注意：**不写** ONNX、TensorRT、C++、CUDA、Docker —— 这些你都没在这个项目里用过。写了就是给自己挖坑。

| 模型规模 | 2.39 M 参数（融合后）/ 5.4 GFLOPs @640 | `docs/inference_benchmark.json` |
| **单张端到端延迟** | **16.4 ms**（FP32，约 61 FPS） | 同上 |
| 批量吞吐 | 每张 7.8~8.8 ms（约 114~128 FPS） | 同上 |

**报数字时的三条纪律**（这是这个项目里最值钱的部分，务必带上）：

1. 报延迟必须带条件 —— 同一份权重、同一张图，换个测法能差 1.45 倍（纯前向 13.8 / 框架推理 10.3 / 端到端 16.4 ms）。**不写条件的"延迟 xx ms"没有意义。**
2. 报 mAP 必须带划分和样本量 —— 验证集是 0.641，测试集是 0.680，两个数不一样；而 AP50 = 0 的 bridges 在测试集里只有 **1 个**标注框，那个 0 不能当结论。
3. 报结论必须带能力边界 —— 见第 5 节。

## 3. 两种讲法

### 3.1 三十秒版（HR 面 / 简历初筛口述）

> "这是我独立做的一个道路场景目标检测项目。数据集是公开的，814 张图、12 个类别。
> 我从整理标注开始做，把原始数据里混着的两种标注格式统一成检测格式，
> 然后训了一个 YOLO26n，在留出的测试集上 mAP50 是 0.68、单张延迟 16 毫秒。
> 但我更想说的是这个项目暴露出来的问题：有四个类别因为样本太少基本没学会，
> 模型也出现了过拟合。我把这些都写进了评估报告的结论里。"

最后那两句是**加分点**，不要省。

### 3.2 三分钟版（技术面）

骨架，具体展开时按对方反应调整：

1. **任务与数据**（30 秒）：12 类道路目标检测；814 张图；标注是 Roboflow 导出的，混着矩形框和多边形两种格式。
2. **我做的第一件事是清数据**（40 秒）：写了脚本把多边形转成最小外接矩形，统一成 YOLO 格式；再做三层校验——格式、坐标越界、空标签。还额外查了数据泄漏（md5 + 感知哈希 + 时间戳），结论是内容层面没重复，但划分存在场景级重叠。
3. **训练**（30 秒）：YOLO26n，50 轮，11 分钟。**重点不是那个 mAP，而是我读出了两个问题**：训练集分类损失一直在降、验证集早就平了（过拟合）；mAP50 在第 19 轮就饱和了，后 30 轮对 mAP50 零贡献 —— 说明瓶颈是数据量不是算力。
4. **评估**（40 秒）：测试集只跑一次。mAP50 0.680。逐类看差距极大：fire hydrants 0.949，bridges 只有 1 个标注框所以 AP 是 0。**我会主动说清这个 0 不可信。**
5. **性能**（30 秒）：测延迟时我踩过坑 —— 第一次测出 23.7 ms，后来复现不出来，查下来是测的时候机器在跑别的任务、而且每组只测了一次。空闲后重测、重复两轮，是 16.4 ms。**这件事教会我：报数字必须连同测量条件一起报。**
6. **边界**（10 秒）：这个项目只做到检测基线，部署（ONNX/TensorRT）我还没做，那是下一步。

## 4. 面试官最可能追问的 10 个问题

| # | 问题 | 答题要点 | 答案在哪 |
|---|---|---|---|
| 1 | mAP50 和 mAP50-95 差这么多，为什么？ | IoU 门槛从 0.5 提到 0.5~0.95 平均，**定位精度**要求陡增。交通信号灯这类小目标定位本来就抖，所以它 mAP50 0.810 但 mAP50-95 只有 0.398 | §2 表 |
| 2 | 为什么测试集是 0.680，验证集只有 0.641？ | 两个划分的样本不同，测试集不一定更难；**我不会拿这个 0.68 去代表"模型水平"**，只能说"在这个划分上" | `metrics_overall.json` |
| 3 | 哪几类学得最差？为什么？ | bridges / chimneys / taxis 垫底，训练框数分别只有 7 / 19 / 14 —— 长尾没救回来。**并且 bridges 在测试集只有 1 个框，那个 0 不能当结论** | 报告第 2 节 |
| 4 | 怎么判断过拟合的？ | 训练集 cls_loss 从 6.04 降到 0.75，验证集在后 30 轮死死卡在 1.08~1.14；框损失末轮训练/验证差 0.224 | §6.2 曲线 |
| 5 | 为什么 mAP50 在第 19 轮就饱和还不早停？ | patience 设了 100，而 mAP50-95 还在慢慢涨，fitness 权重 0.9 偏向 mAP50-95，所以没触发早停。**这说明瓶颈在数据不在算力** | `args.yaml` |
| 6 | 置信度阈值 0.25 是怎么定的？ | 扫 0~1 画 F1 曲线，峰值在 0.30；曲线在 0.2~0.5 很平，所以沿用默认 0.25 没有损失 | `fig_f1_curve.png` |
| 7 | 你这个延迟是怎么测的？ | 三档分开测：`torch.cuda.Event` 纯前向、框架内置阶段拆分、`perf_counter` + `synchronize` 端到端。**三档差 1.45 倍，所以必须先说清测哪一档** | `docs/inference_benchmark.json` |
| 8 | 用 FP16 会更快吗？ | 我这台机器上**没有稳定收益**：单张两轮分别慢 9% 和 71%，纯前向一致偏慢，只有批量下接近。所以我没有采用。**我只有现象，没有做 profiling，不敢解释原因** | 同上 |
| 9 | 怎么保证数据没有泄漏？ | 三层检查：md5 查完全相同（0 组）、感知哈希查近似（0 对）、时间戳邻域查场景重叠（跨划分最近只隔 4.9 秒，1 分钟内 158 对）。**结论是内容层面干净，但不能说测试集完全独立** | `docs/data_leakage_report.json` |
| 10 | 数据集有什么让人意外的地方？ | 它**不是视频抽帧**：814 张图里相邻两张最小间隔 1.09 秒，普遍 5 秒。所以做跟踪演示不能用它，必须另录视频 | `scripts/check_data_leakage.py` 输出 |

## 5. 我的能力边界（这张表背下来）

面试时被问到不会的东西，**直接说"这块我还没做"，然后接上"我的理解是……"**。硬编比坦诚更危险。

### 我在这个项目里真做过、能展开讲的

- 用 Ultralytics 完成一次完整的检测训练与验证：配置、跑、读损失曲线、判断过拟合
- YOLO 标注格式与归一化坐标的换算，以及多边形转最小外接矩形
- 数据质量核查：格式校验、坐标越界检查、空标签排查、数据泄漏检查
- 评估指标的含义与陷阱：P / R / mAP50 / mAP50-95 / F1 / 混淆矩阵方向
- PyTorch 侧的推理计时（三档口径）与"结果必须可复现"的测量纪律
- Python 脚本工程化：argparse、共享配置模块、只读检查脚本、报告自动生成

### 我还没做过、要如实说的

| 没做过的 | 面试时这样说 |
|---|---|
| 从零实现检测网络（backbone / neck / head、损失函数） | "网络结构我用的是框架现成的，没有自己搭过。我理解 YOLO 是单阶段、anchor-free，但具体到每个模块的代码我没写过。" |
| ONNX / TensorRT 导出与量化部署 | "这块是下一步计划，目前只做到了 PyTorch 侧的性能测量。" |
| 多目标跟踪的算法层 | "我跑通了 ByteTrack 的调用链路，但匹配算法本身我没改过，也讲不了它的细节。" |
| 3D 检测 / BEV / 多传感器融合 | "这是车企感知岗的核心方向，我目前只在文献层面了解，没有动手做过。" |
| C++ 推理、嵌入式部署 | "我 C/C++ 有基础，但没做过推理侧的工程实现。" |
