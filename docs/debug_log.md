## 2026-10-13 · 训练报 `missing path`，训练根本起不来

**现象**

从项目根目录启动训练，报错：

```
missing path '...\YOLO_Road_Detection\valid\images'
```

但 `datasets/road-traffic-detect/valid/images` 明明存在。

**原因**

`data.yaml` 里写的是 `path: .`（04 号脚本自动生成的默认值）。
Ultralytics 解析相对 `path` 时按**进程当前工作目录**算，不是按 yaml 所在目录算。

在项目根启动 → 它找 `项目根/valid/images` → 那里没有 `valid` 目录 → 报错。

**处理**

把 `datasets/road-traffic-detect/data.yaml` 的 `path` 改成**绝对路径**。

**验证**

训练正常启动，产出 `runs/.../road_baseline/`。

**现状**

**这个坑仍会复发**：`04_convert_labels_to_detection.py` 生成的 yaml 写的还是 `path: .`。
重跑第 4 步之后必须手动改回绝对路径。已在 README 6.2 明确标注。

## 2026-10-13 · 训练产物路径套了两层 `runs`

**现象**

训练产物出现在 `runs/detect/runs/road_baseline/`，多了一层 `runs`。

**原因**

Ultralytics 的输出目录 = **当前工作目录 + `project` + `name`**。
那次启动时工作目录已经在 `runs/detect` 里，于是 `project=.\runs` 又被套了一层。

**处理**

产物保留在现有位置（不影响使用），并在 README 说明路径成因。
更早一次失败尝试留下的半个目录 `runs/detect/runs/detect/road_baseline/`
（只有 `args.yaml`，`weights/` 是空的）在 2026-10-14 移入回收站。

**验证**

删除前先把里面的 `args.yaml` 归档成 `docs/args_failed_run_2026-10-13.yaml`——
那份文件是"为什么会有这个空目录"的唯一证据，删了就没依据了。

**现状**

已清理。**教训**：训练前先确认当前工作目录，或者干脆用绝对路径写 `project`。

## 2026-10-14 · 根目录多出一份重复的 `yolo26n.pt`

**现象**

项目根目录出现 `yolo26n.pt`，而 `weights/` 里已经有一份。

**原因**

Ultralytics 只按命令里写的路径找权重，**找不到就自动下载一份到当前目录**。
命令里写 `model=yolo26n.pt` 而当前目录没有，它就又下了一份。

**处理**

先确认 md5 与 `weights/` 里那份一致，再移入回收站。之后命令统一写
`model=weights/yolo26n.pt`。

**验证**

md5 比对一致才删，避免删掉唯一正确的权重。

**现状**

已解决。**习惯**：权重路径一律写全，避免重复下载。

## 2026-10-14 · `best.pt` 与 `last.pt` 字节数相同，误以为内容一样

**现象**

两份权重都是 5,469,061 字节，看起来应该完全一致。

**原因**

第 48 轮指标最好（`fitness` 最高）成为 `best.pt`，之后又跑了 2 轮到第 50 轮。
权重数值变了，但序列化后的**字节数没变**。

md5 不同：`974c53ee…` / `e56d3064…`。

**处理**

比较权重一律用 md5 或哈希，不看文件大小。

**验证**

md5 明确不同，说明确实是两次不同的权重。

**现状**

已写入 README 6.3 作为通用提醒。

## 2026-10-14 · 改了标签没删 cache，训练读的还是旧数据

**现象**

修改了 `datasets/road-traffic-detect/` 下的标签文件，重新训练，结果毫无变化。

**原因**

YOLO 第一次读数据后会在标签目录生成 `train.cache` / `val.cache`，
里面是解析好的标签索引。训练直接读缓存，不看 `.txt`。

**处理**

```bash
rm datasets/road-traffic-detect/train/labels/train.cache
rm datasets/road-traffic-detect/valid/labels/val.cache
```

**验证**

删缓存后重新训练，指标发生变化。

**现状**

已写入 README 6.1 作为固定检查项。

**现状**

## 2026-10-14 · 数据泄漏检查：内容干净，但时间戳完全重叠

**现象**

需要确认 train / valid / test 之间有没有重复图片。

**原因**

如果测试集里混了训练集的图，报出来的 mAP 就是虚高的。

**处理**

写 `check_data_leakage.py` 做三重检查（md5 / dHash / 时间戳邻域）。

**验证结果**

| 检查 | 结果 | 解读 |
|---|---|---|
| 内容 md5 | 跨划分 **0 对** | 没有完全相同的文件 |
| dHash（阈值 5） | 跨划分 0 对；最接近一对距离 **15** | 没有画面近似的重复；距离 15 说明检查有区分度 |
| 时间戳 | 三划分跨度**完全重叠**（2022-05-23 ~ 2022-07-01），最近一对隔 **4.9 秒**，1 分钟内 **158 对** | 可能是同一段采集被随机切到不同划分 |

**结论必须分两句说**：

- 内容层面：**干净**，没有重复
- 划分方式：**按图随机切**，存在轻度场景重叠的风险，测试指标要按**偏乐观**理解

时间戳靠得近只是**弱证据**，不等于画面重复。这句边界不能省，
否则就是把检查结果说过了头。

**现状**

**已知边界**。待办里已列"补一条场景级去重办法（按采集批次分组后再划分）"，
并注明：**重新划分后现有指标不能直接对比**，必须重新评估并标注「旧划分下的结果」。

## 2026-10-27 · `.engine` 反序列化报 magicTag 不匹配，看着像版本不对

**现象**

用 TensorRT 直接读 Ultralytics 导出的 `best_fp32.engine`：

```
plan->header.magicTag == rt::kPLAN_MAGIC_TAG failed
... incompatible serialization version
```

报错完全指向"TensorRT 版本不匹配"，容易让人去换 TRT 版本。

**原因**

Ultralytics 写出的 `.engine` **不是纯 plan**。它在 plan 前面加了
`[4 字节长度][JSON 元数据]`（本项目是 `0x30F` = 783 字节），描述导出参数。
直接从文件开头读，等于把元数据当成 plan。

**处理**

先探测前 4 字节当作长度、跳过 `4 + N`，再试反序列化；读不到就退回"整个文件读"。

**验证**

`15_verify_engine.py` 改成探测式读取后，FP32 / FP16 两个引擎都能正常加载，
结构层输出与 ONNX 完全一致。

**现状**

✅ 已解决。这个报错**一个字都没提"文件前面有头"**，是本次排查里最耗时的一个。

## 2026-10-27 · TensorRT 引擎建好了、`ep` 也显示 TensorRT，但速度还是 CUDA 的

**现象**

补齐 `nvinfer` / `cudnn` / `cublas` 之后，推理仍是 8–10 ms，而不是预期的 3 ms。
**不报错、不抛异常、`ActualEP` 显示正常。**

**原因**

ORT 的 TensorRT EP 在加载失败时**静默回落**到 CUDA EP。
缺 `nvrtc64_120_0`（tactic 要运行时 JIT 编译）时，它就是"能跑，但没有 TRT 的加速"。

**处理**

1. 节点/程序里加启动自检：跑 25 帧空白图，若延迟明显偏离该后端的量级就打印警告
2. 验收判据从"EP 名字对不对"改成"**延迟落没落在 2–4 ms**"
3. 补 `nvrtc` 与 `nvJitLink`

**验证**

补齐后 `infer p50` 从 8–10 ms 降到 1.97 ms（Python）、3.22 ms（C++ TRT EP）。

**现状**

✅ 已解决，但**同类风险永远存在**——换成新机器、新驱动仍可能静默回落。
所以 `sanity_check()` 这个设计保留在 ROS2 节点里。

## 2026-10-28 · 分发包里跑 `--ep trt` 得到 5.25 ms，看着"能用但慢"

**现象**

把 `cpp/dist/` 拷到干净目录，`--ep trt` 跑出来 5.25 ms。
既不像 TRT（2.35），也不像 CPU（19），卡在中间。

**原因**

`dist/` 里的 `yolo_cpp.exe` 是 **387 KB 的旧版**，`build/` 里是 **443 KB**。
用 `strings` 比一下，旧版**根本没有 `--ep` 这个字符串**——它是加 TensorRT 支持之前打的包。
所以参数被解析器忽略，实际走的是 CUDA EP。

**整个过程不报错**：正常启动、正常出框、正常打印耗时，只是跑的不是你以为的那条路。

**处理**

写 `cpp/collect_deps.py` 打包，自动记录每个文件的 sha256 到 `MANIFEST.txt`；
`--check` 会比对"包内 exe 与 build 是否同一 sha256"。

**验证**

`--check` 能同时报出"缺哪些 DLL"和"exe 是否过期"。重建后 CPU 包 143 文件 / 212.9 MB，
干净 PATH 下验证通过。

**现状**

✅ 已解决。**教训：手工维护的分发包一定会漂移**，必须让脚本比对版本。

## 2026-10-28 · 用 `nvidia-smi` 前后各读一次，算出"模型几乎不占显存"

**现象**

想测显存占用：跑之前读一次 `nvidia-smi`，跑之后读一次，差值就是模型占的。
实测「推理前 1621 MB → 程序退出后 1612 MB」= **−9 MB**。

**原因**

两个独立的错误叠在一起：

1. **程序退出时 CUDA 把显存全部释放**，两头都是"空的"；而 `nvidia-smi` 读的是**整卡总量**，
   不是某个进程的分配量。
2. **测量开销太大**：单次调用 101–107 ms，而一帧推理只有 2–3 ms——测量开销是被测对象的 30–50 倍。

**处理**

改用 `cudaMemGetInfo`，运行时动态加载（Windows `LoadLibrary` / Linux `dlopen`），
不增加编译期依赖；视频循环里每 100 帧采一次。

**验证**

1000 帧：`at_start` 1665 → `first_sample` 1691（加载+预热只多占 26 MB）→ 第 1000 帧仍 1691，
净增 **0 MB**，10 次采样完全一致。找不到 `cudart` 时显示"显存不可用"，程序照常跑完。

**现状**

✅ 已解决。**判据也随之改了**：查泄漏看 `first → last` 有没有增长，
**不是**看程序前后的总数（后者在稳态下永远是 0）。

## 2026-10-29 · 用 640×640 的图测 letterbox，测了个寂寞

**现象**

想验证 letterbox 的坐标反变换对不对，用项目的 187 张验证图跑，框位置全对，
于是认为"坐标变换没问题"。

**原因**

那 187 张图**全是 640×640**，而模型输入也是 640×640：

```
scale = min(640/640, 640/640) = 1.0
pad_x = pad_y = 0
反变换 x = (x - 0) / 1.0 = x     ← 恒等映射
```

**scale 和 pad 即使全算错，这批图也测不出来。** 这是测试设计里的"用例没有分辨力"：
跑通了，但没证明任何事。

**处理**

人为造非方形输入：`fake_camera.py --size 960x540` →
`scale = 0.6667`、`pad_y = 140`。这时框的位置才真正依赖变换公式。

**验证**

非方形输入下若框整体上下偏约 140 px，就是 `pad_y` 错；整体偏大偏小则是 `scale` 乘除搞反。
单元测试 `test_letterbox.cpp` 里本来就覆盖了非方形用例，是这次才意识到它为什么重要。

**现状**

⚠️ 已知边界。**用正方形输入验证不了 letterbox** 这件事本身不会"修好"，
只能在验证流程里记住：改坐标相关代码，必须用非方形输入复测。

## 2026-11-20 · 报告里写"熵校准"，实际是 MinMax

**现象**

构建 INT8 引擎时脚本注释写的是"PTQ + 熵校准（IInt8EntropyCalibrator2）"，构建成功、指标也正常。
但 TensorRT 日志里有一行：`Writing Calibration Cache for calibrator: TRT-100800-MinMaxCalibration`。

**原因**

ultralytics 的导出器把校准算法**写死**成 `MINMAX_CALIBRATION`（只有 DLA 场景才切 `ENTROPY_CALIBRATION_2`），
校准器还是函数内部的嵌套类，外部没有开关。**代码里没有传校准算法的地方，注释写的不算数。**

**处理**

报告与文档改成实际值（MinMax），并把日志原文一起记进 JSON，便于以后核对。

**验证**

`docs/deployment/engine_int8_export_report.json` 的「量化方式」与「校准日志关键行」两个字段。

**现状**

✅ 已修正。**教训：凡是"用了什么算法/开了什么开关"的结论，必须去日志或产物里找证据，
不能凭注释或参数名推断。**
